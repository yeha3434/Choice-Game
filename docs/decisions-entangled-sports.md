# 选什么 · 决策记录

- 日期：2026-10-30
- 当前阶段：阶段 4（公平比赛引擎）等待用户验收
- 实施状态：阶段 0～3 已提交；阶段 4 已实现并验证，尚未提交

## 已确定

### 产品目标

- 制作一个轻松、搞怪、可爱的网页决策小游戏。
- 用户输入 2～4 个选项，每个有效选项成为一名选手，通过一场约 15～20 秒、有领先变化和随机事件的赛跑决定结果。
- 重点是让观看比赛的过程有趣，而不只是随机显示答案。
- 用途保持通用，不使用限制具体场景的宣传语。
- 第一版只实现赛跑模式；弹珠赛道、抢椅子等不提供占位入口。

### 平台与数据

- 第一版是适配电脑和手机浏览器的网页 App。
- 不需要登录，不制作原生安装包。
- 选项、角色和比赛均在客户端完成。
- 音乐与音效分别提供开关，并记住设置。

### 输入与角色

- 默认两个输入框，至少保留两个，最多四个；允许增加和删除多余输入框。
- 忽略空白项；至少两个有效选项才能开始。
- 每个有效选项对应一名角色和一条跑道。
- 四个原创卡通角色为：大眼仔、肚肚侠、长腿哥、淡定薯。
- 角色随机且不重复，开赛前允许手动更换。
- 角色只改变表现，不改变胜率。

### 比赛表现

- 跑道从上到下排列，选手从左向右跑。
- 场景是暖橘色、略显不正规的社区运动会。
- 比赛包含倒计时、起跑、途中和冲刺；需要领先变化、皇冠转移、随机事件及清楚的冲线过程。
- 加速、摔跤、疲惫和冲刺必须有明显不同的动作反馈。
- 香蕉皮、水坑、风扇等障碍必须和触发动作对应。
- 角色摔倒与恢复动作体现各自特点。
- 手机竖屏仍需保持选项名称、角色和比赛状态可读。

### 公平性与结果

- 所有有效选项获胜概率相同。
- 角色、跑道和出发位置没有固定优势。
- 画面实际冲线顺序必须与结果一致。
- 第一版不提供影响胜率的手动加速。

### 结果与重玩

- 获胜角色撞开彩带、展示对应选项并进行胜利动作。
- 提供“就这么办”“不服，再来一局”“修改选项”三个操作。
- 重玩保留选项并重新随机比赛。
- 返回修改时回到输入界面。
- 比赛中禁止重复开始；重玩必须清理上一局动画、事件、计时器和声音。

### 音频

- 使用原创合成音乐与音效，优先采用 Web Audio API，不依赖付费或未经授权的素材。
- 倒计时、起跑、加速、摔跤、领先变化、冲刺和获胜均有对应声音。
- 首次播放等待用户点击，兼容手机浏览器自动播放限制。
- 静音时不影响游戏流程；不同界面或重玩时不重复叠加背景音乐。

### 验收底线

- 2、3、4 人比赛都能完成。
- 输入校验、增加删除选项、换角色正常。
- 加速、摔倒、冲刺动作清晰可见。
- 获胜结果与实际冲线顺序一致。
- 连续重玩不发生计时器、动画或音频叠加。
- 音乐和音效开关独立有效并能记住。
- 电脑和手机均可正常操作。

### 开发流程

- 需求澄清完成后先比较 2～3 套技术方案，优先推荐最简单、最容易维护的方案。
- 用户选定技术方案后再拆分功能，不提前写代码。
- 每次只实现一个小功能；完成后运行相应测试并提供证据。
- 等用户确认该功能后再提交 Git，然后继续下一项。

## 2026-10-30 补充决定

- 产品标题：使用中文“选什么”，三个字采用错位、旋转、描边和彩色厚阴影的夸张招牌表现。
- 目标用户：中文、全年龄普通用户。
- 响应式基线：最低宽度 360px；支持较新的 Chrome、Edge、Firefox、iPhone Safari 和安卓浏览器；不兼容 IE 和过旧浏览器。
- 重复选项：去除首尾空格后，完全相同的选项不允许开赛，并显示明确提示。
- 名称处理：最多约 40 个字符；赛道标签最多两行，过长时省略；结果界面显示完整名称；特殊字符只作为文字处理。
- 公平随机：开赛时使用浏览器安全随机能力，在有效选项中等概率确定获胜者，再生成与该结果一致且包含悬念的比赛时间线。
- 比赛引擎：先锁定冠军并随机排列其余名次，再生成约 18 秒的起跑、途中、冲刺和冲线数据；表现层不能改写结果。
- 公平提示：界面只简短说明“每位选手机会相同”，不显示复杂概率或随机种子。
- “就这么办”：锁定当前结果，显示“决定已确认”，保留“修改选项”；第一版不做分享、结果图片或历史记录。
- 持久化：刷新后不保留选项和比赛结果；只长期保存音乐与音效开关。
- 声音默认开启，但必须等待用户第一次点击后播放；分别记住音乐和音效设置。
- 无障碍：尊重系统的“减少动态效果”偏好，减少背景移动和摇晃，但保留比赛流程与关键动作。
- 视觉资产：角色、跑道、观众和领奖台全部使用原创内联 SVG 与 CSS，不加载外部图片、字体或素材包。

## 2026-10-30 Grill 第二轮结论

- 学习参与方式：采用“共同驾驶”。Agent 先解释关键命令和修改，再执行；重要 Git 操作由用户确认，过程中安排少量、可跳过的小练习。
  - 理由：兼顾实际进度和真正理解，避免完全旁观或被操作门槛卡住。
- 第一版交付：先在本机完成和验证，再发布为可分享的公开网页链接。
  - 理由：能完整学习从本地开发、Git 版本管理到 GitHub 和静态部署的交付流程。
- 开发节奏：学习优先，接受更多阶段、验证和确认点，不采用一次性生成完整项目的方式。
  - 理由：Git、测试和需求决策需要在真实增量开发中学习，事后补历史无法达到同样效果。
- 结果界面：重点庆祝冠军，同时显示完整冲线排名。
  - 理由：增加比赛感，也让用户能核对画面顺序和结果数据一致。
- Grill 结论：常规强度下，剩余产品未知不足以明显改变下一步，需求澄清结束。

## 技术方案候选

### 方案 A：Vite + 原生 TypeScript + SVG/CSS（推荐）

- 界面：语义化 HTML 和响应式 CSS。
- 角色与场景：内联 SVG；动作主要使用 CSS transform/animation，由 TypeScript 控制状态。
- 比赛逻辑：无框架 TypeScript，公平随机、事件时间线和动画表现分层。
- 音频：Web Audio API 原创合成。
- 测试：Vitest 测纯逻辑；Playwright 在真实浏览器验证完整流程、手机尺寸、截图和控制台错误。
- 部署：纯静态网站，不需要服务器、数据库、账号或密钥。
- 主要优点：依赖少，能直接学习 HTML、CSS、TypeScript、浏览器 API、测试和 Git；代码与画面关系容易理解。
- 主要风险：动画状态和计时器需要自己设计清楚，但本项目只有最多四名选手，范围可控。

### 方案 B：Vite + React + TypeScript + SVG/CSS

- 在方案 A 基础上用 React 管理输入页、比赛页、结果页和角色组件。
- 主要优点：组件化明显，未来增加多种小游戏时更容易复用界面与输入状态，也能顺便学习 React。
- 主要风险：需要同时学习 React 状态、副作用和生命周期；音频、动画和计时器清理更容易被框架细节干扰，第一版复杂度偏高。

### 方案 C：Phaser + TypeScript

- 使用专门的 2D 网页游戏框架处理场景、时间线、镜头和 Canvas 渲染；输入与结果界面仍需配合普通 HTML。
- 主要优点：适合大量精灵、关卡、粒子和物理效果，未来扩展为多个重度小游戏更方便。
- 主要风险：框架学习成本最高；表单、长文字、响应式排版和无障碍不如 DOM/SVG 直接；对当前最多四人的小游戏属于过度设计。

### 当前推荐

- 已于 2026-10-30 选择方案 A。
- 起决定作用的理由：它能完整实现第一版，同时让用户看清网页、动画、随机逻辑、测试和 Git 的每一层，不会先被 React 或游戏引擎的抽象挡住。
- 技术栈：Vite、原生 TypeScript、语义化 HTML、响应式 CSS、内联 SVG、Web Audio API、Vitest、Playwright。
- 运行形态：纯静态网页；不使用后端、数据库、账号、云同步或运行时密钥。
- 用户需要维护：项目源代码、npm 依赖更新、测试和静态网站部署；无需维护服务器和数据库。
- 主要风险：角色动画、事件时间线、音频和重玩清理均由项目自行管理，因此必须分层设计并用自动化测试防止状态叠加。
- 仍会改变核心技术方案的待定问题：无。
