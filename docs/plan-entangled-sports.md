# 《纠结运动会》第一版实施与学习计划

- 状态：阶段 0 已实现并验证，等待用户确认后首次提交
- 原则：一次只实现一个阶段；验证通过后由用户确认；确认后才提交 Git 并进入下一阶段。
- 技术方案：Vite + 原生 TypeScript + SVG/CSS + Web Audio API + Vitest + Playwright。

## 每个阶段的固定循环

1. 先说明这一阶段解决什么问题、会修改哪些文件、会学到什么。
2. 开始前运行 `git status`，确认工作区状态。
3. 只实现本阶段范围，不顺手加入后续功能。
4. 运行类型检查、相关单元测试或浏览器测试。
5. 对可见界面进行浏览器操作；检查控制台；保存必要截图。
6. 展示 `git diff`，用白话解释关键修改。
7. 按固定格式交差：做了什么、测试结果、截图、没验证到的内容。
8. 等用户确认。
9. 用户确认后执行 `git add` 和 `git commit`，再进入下一阶段。

## 阶段拆分

### 阶段 0：Git 仓库和项目骨架

- 当前状态：实现完成；构建、Vitest 和真实 Edge 冒烟测试通过；尚未提交。
- 目标：建立一个能启动、能构建、能测试的空白网页项目，但不制作游戏界面。
- 内容：初始化 Git；创建 Vite 原生 TypeScript 项目；配置 `.gitignore`、Vitest、Playwright 和基础目录；保留现有 `docs`。
- 验收：开发服务器能打开；生产构建成功；空白示例测试通过；Git 能正确忽略依赖和测试产物。
- 学习重点：仓库、工作区、暂存区、提交、`.gitignore`、`git status`、`git diff`。
- 建议提交：`chore: initialize project and test tooling`

### 阶段 1：选项输入框

- 目标：完成默认两个输入框，以及添加和删除选手。
- 内容：至少保留两个输入框，最多四个；暂不开始比赛。
- 验收：增加、删除和数量边界正常；360px 手机宽度可操作。
- 学习重点：一次提交只解决一个用户行为；HTML、CSS、TypeScript 的职责区别。
- 建议提交：`feat: add option entry controls`

### 阶段 2：输入校验与比赛准备数据

- 目标：把输入转换成可靠的参赛选项。
- 内容：忽略空白、至少两项、拒绝重复、限制长度、特殊字符按文字处理；开始按钮只在有效时可用。
- 验收：正常、空白、重复、超长和特殊字符测试通过；错误提示明确。
- 学习重点：纯逻辑函数、单元测试、边界情况和“测试用户能感受到的行为”。
- 建议提交：`feat: validate race options`

### 阶段 3：四个角色与赛前换人

- 目标：绘制四个有辨识度的原创 SVG 角色，并完成不重复随机分配和手动更换。
- 内容：大眼仔、肚肚侠、长腿哥、淡定薯的静态造型；两到四人赛前预览；角色不重复。
- 验收：四个角色可凭造型区分；2、3、4 人分配均无重复；换人不会产生冲突。
- 学习重点：SVG 结构、可复用渲染函数、数据与视觉分离。
- 建议提交：`feat: add racer characters and selection`

### 阶段 4：公平比赛引擎

- 目标：先实现不依赖画面的公平随机和比赛时间线数据。
- 内容：用安全随机能力等概率选择冠军；为全部选手生成起跑、途中、冲刺和冲线数据；结果排序与预定冠军一致；测试可注入固定随机源。
- 验收：2、3、4 人逻辑测试通过；角色和跑道不影响胜率；相同测试随机源得到可重复结果。
- 学习重点：为什么先测逻辑再做动画；随机与可测试性的冲突如何解决。
- 建议提交：`feat: add fair race simulation engine`

### 阶段 5：响应式跑道和静态场景

- 目标：在电脑和手机上清楚展示全部选手和运动会场景。
- 内容：暖橘色跑道、歪白线、起点横幅、终点彩带、领奖台和少量观众；2～4 条跑道自适应；长名称不遮挡角色。
- 验收：360px 手机和桌面宽度截图可读；所有选手始终可见；画面不过度拥挤。
- 学习重点：响应式布局、视觉层级、浏览器截图验证。
- 建议提交：`feat: build responsive race stadium`

### 阶段 6：倒计时、基础跑动和皇冠

- 目标：让数据时间线第一次变成可观看的比赛。
- 内容：3、2、1 倒计时；从左向右的非匀速跑动；阶段切换；领先皇冠随排名转移；终点前保持悬念。
- 验收：正式比赛约 15～20 秒；存在明显领先变化；重复点击不会重复开赛；结果与冲线顺序一致。
- 学习重点：动画循环、状态机、计时器生命周期和浏览器性能。
- 建议提交：`feat: animate core race flow`

### 阶段 7：随机事件和障碍物

- 目标：增加有因果关系、但不破坏公平结果的比赛事件。
- 内容：加速、摔跤、疲惫；香蕉皮、水坑、风扇；气泡和速度线；事件数量与音效触发节流。
- 验收：每类事件清楚可见；障碍和动作对应；气泡不遮挡关键画面；最终结果不被事件系统改写。
- 学习重点：事件队列、表现层与结果层分离、如何控制随机内容。
- 建议提交：`feat: add race events and obstacles`

### 阶段 8：角色专属动作

- 目标：让四个角色的跑步、摔倒、恢复和冲刺方式明显不同。
- 内容：脑袋晃动与偷看、肚子弹动、长腿打结、土豆翻滚等专属动画。
- 验收：不看名字也能认出角色；加速、摔倒和冲刺动作清楚；减少动态模式仍可理解事件。
- 学习重点：CSS/SVG 动画组合、复用与特例之间的边界。
- 建议提交：`feat: animate unique racer personalities`

### 阶段 9：冲线、结果和重新选择

- 目标：完成从冲线到确认、重赛和修改选项的闭环。
- 内容：冠军撞开彩带、胜利舞、失败动作、完整排名；三个结果操作。
- 验收：“就这么办”锁定结果；重赛保留选项；修改选项返回输入界面；完整排名与冲线一致。
- 学习重点：页面状态转换、用户流程测试和避免隐藏状态残留。
- 建议提交：`feat: add results and replay choices`

### 阶段 10：音乐与音效

- 目标：用 Web Audio API 加入原创合成声音，并保持可控。
- 内容：输入音乐、倒计时、起跑、比赛、加速、摔倒、领先、冲刺和获胜声音；音乐与音效独立开关；记住设置。
- 验收：用户点击前不自动播放；静音不影响游戏；切换页面和重玩不会叠加背景音乐；开关刷新后保留。
- 学习重点：浏览器音频限制、资源清理、`localStorage`。
- 建议提交：`feat: add synthesized music and sound effects`

### 阶段 11：连续重玩与资源清理

- 目标：专门验证并加固动画、计时器、事件和音频的清理机制。
- 内容：统一的比赛会话取消与清理；为自动化测试提供仅测试环境可用的加速时钟，不改变正常游戏时长。
- 验收：至少连续重玩五局，无重复计时器、重复事件、音频叠加或旧皇冠；测试故意制造旧会话时必须能发现问题。
- 学习重点：回归测试、把重复错误变成自动检查。
- 建议提交：`fix: harden race session cleanup`

### 阶段 12：最终浏览器验证与发布准备

- 目标：完成第一版的跨浏览器、手机和生产构建验证。
- 内容：Playwright 覆盖 2、3、4 人；桌面与手机尺寸；控制台错误；减少动态模式；README 启动说明；部署配置候选。
- 验收：类型检查、单元测试、端到端测试和生产构建全部通过；关键流程有截图证据；未验证项明确列出。
- 学习重点：`prove-it`、发布前检查、分支合并和版本标签。
- 建议提交：`test: verify complete race experience`

### 阶段 13：公开部署

- 目标：把已验证版本发布为可分享链接。
- 内容：根据目标地区选择静态托管平台；建立部署流程；从公开地址再跑一次关键流程。
- 验收：公开链接可访问；手机和电脑可完成一局；刷新与静态资源路径正常。
- 学习重点：GitHub 远程仓库、push、部署、发布后的验证。
- 建议提交：`chore: configure static deployment`
